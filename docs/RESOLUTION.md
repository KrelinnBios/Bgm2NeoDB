# 条目匹配与恢复设计

## 目标与边界

将已核实的匹配过程纳入程序，避免依赖临时脚本。自动迁移只接受唯一、同类型的对应关系。版本歧义由用户确认；用户提交作品外链时，程序只请求已连接的 NeoDB 实例按其支持的来源抓取或创建条目，程序本身不直接创建条目。

搜索无匹配、分页未读完和抓取超时都不能证明目标实例未收录作品。程序记录实际结果，不把这些情况统称为“成人条目不支持”。

## 现有模块分工

| 模块 | 职责 |
|---|---|
| `app/bangumi.py` | 用用户自己的 Bangumi 凭证读取收藏和条目详情。详情 404 时仍可利用收藏中的名称。 |
| `app/neodb.py` | 搜索分页、条目解析、同实例链接验证、请求 NeoDB 抓取外链、读取和写入收藏。保留来源链接；不直接创建 NeoDB 条目。 |
| `app/resolution.py` | 从官方详情提取别名，收集候选，产生明确的匹配决定；不写入收藏。 |
| `app/database.py` | 按账号组合保存详情缓存、候选、匹配依据、人工确认和原有迁移状态。 |
| `app/migrator.py` | 选择可重试条目、控制等待时间、登记匹配结果、准备写入及回读核对。 |
| `app/routes.py` / `static/app.js` | 在现有详情对话框展示保存的候选，提供重新查找和确认选择。 |

## 决定顺序

1. 已保存的人工映射继续使用；写入前刷新条目，作品合并后仍遵循人工选择。
2. 读取收藏名称及 Bangumi 详情中的正式名称、`infobox` 的“别名”。描述、作者名不作为标题。
3. 搜索词中的 ASCII 连字符替换为空格；最终匹配仍使用原有标题规范化规则。
4. 汇总每个查询的分页结果，按 UUID 去重。最多六个查询、每个查询三页。达到上限或存在无法解析的结果时标记 `incomplete`，不声称唯一匹配。
5. 在同类型候选中优先选择指向当前 Bangumi ID 的来源链接。仅识别 Bangumi 的三个已支持域名和 `/subject/{id}` 路径。
6. 没有来源链接匹配时，检查官方名称和别名的精确匹配。明确关联其他 Bangumi ID 的候选不会因为同名而被选中。
7. 多个匹配候选保留给用户确认。不能先排除重复目标，再把另一个版本当成唯一答案。
   候选是否已在用户的 NeoDB 收藏中不作为作品身份依据，不会查询全部候选的收藏状态来推断匹配。旧版尚未完成的 `external_shelf` 映射会重新解析，已完成记录不自动重写。
8. 自动匹配仍须判重；用户点击“确认选择”属于明确覆盖决定，只处理当前条目并按所选目标写入。
9. 搜索无匹配时可调用原有 `catalog/fetch`；临时处理中的地址继续受最终阶段整批 60 秒预算约束。

## 持久化结果

`entries` 以兼容旧数据库的方式增加两个可空 JSON 列：

- `subject_detail`：Bangumi 详情缓存；重新扫描时失效，收藏原文保存在当前扫描记录中。
- `resolution`：`code`、`message`、`retryable`、`basis`、`candidates`、`item`，以及检查时间与查询标题等补充信息。

人工确认用 `basis=manual` 标识，重新扫描保留其映射依据。候选持久化在本地，页面重新打开无需再次访问外部站点即可查看。

| 结果 | 自动继续时的处理 |
|---|---|
| `matched` | 已准备的映射进入原有写入和回读核对流程。 |
| `ambiguous` | 显示冲突与候选，等待确认。 |
| `no_match` | 抓取也未找到后保留原因；用户可主动重新查找。 |
| `incomplete` / `invalid_response` / `request_rejected` | 保留原因，避免在证据不完整时自动写入。 |
| `transient` / `fetch_timeout` | 可重试，保留已有候选。 |

收藏写入失败或回读不一致仍按原有恢复流程处理，不因匹配阶段成功而被排除在重试之外。

## 并发和界面

- 匹配阶段不发送收藏写入请求。已经开始写入的条目不受解析超时取消。
- 解析最多 4 项同时进行，解析名额在进入写入阶段前释放，写入及核对最多 8 项同时进行。写入前回读发现目标合并时，再次登记占用，避免并发覆盖另一个条目的目标。
- 单条详情读取按账号和条目编号查询，判重用已迁移目标索引，并排除旧扫描与其他账号的数据。
- 手工映射和主动查找候选在迁移空闲时进行，使用现有任务锁，避免与任务启动竞争。
- 自动匹配的重复目标会保留冲突；人工确认后按用户选择处理当前条目，不启动整批任务。
- `resolve_failed` 和 `conflict` 都可打开候选选择。候选链接可用于查看版本详情。
- 无可自动重试条目时，主按钮提示先确认待处理条目；确认选择后只启动当前条目的迁移。
- “按链接导入”同时接受完整 HTTP/HTTPS NeoDB 条目链接和外部作品来源链接，复用现有映射接口及单条任务。已有条目直接解析；未收录的普通作品先请求 NeoDB 抓取，再返回抓取中的状态，页面每隔至少 15 秒自动检查一次，最多等待 60 秒并显示倒计时，避免把映射请求阻塞在 NeoDB 的后台任务上。程序不直接提交创建表单；详情中的“在 NeoDB 创建条目”按钮会按 Bangumi 类型打开对应创建页面，创建完成后可粘贴 NeoDB 条目链接绑定。
- 外链仅作为 `catalog/fetch` 的查询参数发给已连接的 NeoDB 实例，本机不携带 NeoDB 凭证访问来源站点，返回条目和跳转仍校验同实例。无效链接、不支持的来源、授权失效或超时均不覆盖原映射、不启动收藏写入。
- 弹窗在链接解析提示旁显示倒计时，从提交起最多等待 60 秒（包括请求和重试间隔）；超时停止本页等待及轮询，恢复操作按钮。超时或解析失败后保留具体原因和输入，提示用户在 NeoDB 手动创建后粘贴条目链接。NeoDB 已接收的后台抓取无法由页面取消。链接解析成功后按用户选择保存人工映射，并使用页面上的日期导入设置启动当前条目任务。
- 条目详情根据 Bangumi 类型和平台信息提供 NeoDB 创建入口：书籍→Edition、音乐→Album、游戏→Game；动画及三次元作品按平台判断为 Movie、TVShow 或 Performance。平台信息不足以判断时不显示入口，避免猜测错误。标题经过 URL 编码并使用当前已连接的 NeoDB 实例。

## 接口依据与验证

使用现有本地 OpenAPI 快照中的 `GET /v0/subjects/{subject_id}`、`GET /api/catalog/search` 的 `page` 参数及已有收藏接口。没有增加外部接口。

测试覆盖来源优先、同名不同来源、多个候选与重复目标、搜索分页及截断、正式别名、临时错误恢复、人工映射覆盖已迁移目标及跨扫描保留、季度链接，以及原有的授权失效、隐私、断点恢复、合并跳转和写后核对。

这些检查保证程序的匹配和恢复行为，不承诺所有 Bangumi 条目都能在目标实例找到对应作品。
